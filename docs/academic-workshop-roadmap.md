# ROADMAP

Планы развития академической мастерской (academic-workshop).

Документ состоит из двух частей: **дорожная карта по этапам** (что делать и в каком порядке) и **тематические спецификации** (разделы 1–6 — детальное устройство каждой подсистемы).

## Инфраструктура: скиллы, плагины и Claude Code Web

Часть скиллов в `.claude/skills/` дублирует то, что уже даёт плагин `superpowers` (`brainstorming`, `executing-plans`, `using-git-worktrees`, `using-superpowers` и другие) — для локальной работы через CLI плагина достаточно, эти копии избыточны.

Причина, по которой сырые копии всё же лежат в репозитории: **Claude Code Web не имеет доступа к плагинам**. Проекты, работающие через веб-сессии, не могут подключить `superpowers` как плагин — им нужны файлы скилла прямо в `.claude/skills/`.

**Не сделано, идея на будущее:** скрипт, который при старте веб-сессии наполняет `.claude/skills/` копиями скиллов из плагинов (`superpowers`, возможно `academic`), но **не по умолчанию** — при локальной работе через CLI плагины уже покрывают эти скиллы, дублировать их не нужно.

## Дорожная карта по этапам

### Принципы

1. **Единая шина данных.** Метки предложений и CSV из раздела 1 — общий формат, в который пишут и из которого читают все остальные подсистемы. Сначала строим её, потом наращиваем.
2. **Вертикальные срезы.** Каждая фаза заканчивается артефактом, которым уже можно пользоваться на реальном тексте, а не наполовину готовой подсистемой. Лучше узкий сквозной поток, чем широкий, но неработающий.
3. **Стоимость растёт по фазам.** Сначала дешёвые LLM-проверки (перевод, прогон на примере), дорогая формальная верификация в Lean — позже, поверх уже отлаженной разметки.
4. **Каждая фаза опирается на предыдущую**, но даёт самостоятельную ценность: на любой фазе можно остановиться и иметь рабочий инструмент.

### Фазы

| Фаза | Цель (что появляется) | Тянет из разделов | Definition of Done |
|---|---|---|---|
| **0. Подстрочник MVP** | Один Typst-документ: под размеченным предложением — перевод | 1.1, 1.2 | Компилируется PDF; режимы `draft`/`translation` работают на минимальном CSV |
| **1. Контекст и автозаполнение** | CSV наполняется полуавтоматически; контекст выгружается в LLM | 1.3, 1.5 | `populate_context.py` считает `active_until`; `context-dump` даёт JSON на метку; skill предлагает переводы/комментарии |
| **2. Внешние знания** | Подсказки готовых лемм при письме | 2 (целиком) | `/stack-lookup` возвращает теги + URL; колонка `stacks_ref` автозаполняется |
| **3. Проверка «на примере» (дёшево)** | Каждое доказательство прогнано на конкретном объекте; видны пробелы | 5, 3.4 (Rethlas) | Режимы `parallel`/`inline-example`; `gap-check` подсвечивает незаполненные шаги |
| **4. Формальная верификация (дорого)** | Ключевые леммы `verified` в Lean; кросс-чек с примером | 3, 5.4 | Иконки статусов в PDF; аннотация «N из M верифицированы»; расхождение пример/Lean ловится |
| **5. Вывод: доклад + единый `review`** | Из одного источника — и статья-ревью, и доклад | 4, 1.4 | Один подстрочник → `review`-PDF и `slides` + `notes` |
| **6. Сквозная оркестрация** | Проект ведётся от вопроса до публикации одним оркестратором | 6 + `academic-*` скиллы | `state.yaml` отражает стадии; сводка «из N подвопросов K закрыто» |

### Что отдаём после каждой фазы

```
Ф0 → размеченный текст с переводом              (можно читать билингву)
Ф1 → + автоперевод и контекст для ИИ            (можно подключать агентов)
Ф2 → + ссылки на Stacks/внешние базы            (можно искать аналоги лемм)
Ф3 → + прогон доказательств на примере          (можно ловить дешёвые ошибки)
Ф4 → + формальные статусы Lean                  (можно заявлять верификацию)
Ф5 → + доклад и сводный review                  (можно выступать и рецензировать)
Ф6 → + журнал стадий вопрос→статья              (можно вести проект целиком)
```

Границы фаз совпадают с уже намеченным «рекомендуемым порядком» (см. ниже), но переформулированы как сквозные срезы: внутри одной фазы трогаем сразу несколько разделов ровно настолько, насколько нужно для следующего работающего артефакта.

## 1. Подстрочник: система меток и локального контекста в LaTeX/Typst

### Идея

Для каждого предложения (утверждения, определения, леммы) в тексте назначается уникальная метка. Метки населяются данными из внешнего файла (CSV или YAML): переводы, комментарии ИИ, статус верификации, история правок. Дополнительно вводится понятие **локального контекста** — набора объектов и свойств, актуальных в данной точке текста.

### Компоненты

#### 1.1 Разметка предложений

- Макрос `\sent{label}{text}` (LaTeX) / функция `sent(label, text)` (Typst), которые:
  - размещают невидимую метку рядом с предложением (anchor),
  - при включённом режиме `draft` отображают метку на полях,
  - при режиме `interlinear` добавляют строку с переводом/комментарием под предложением.
- Метки именуются в стиле `sec2.def.topology` или просто `s001`, `s002` — на усмотрение автора.

#### 1.2 Внешний файл данных (CSV / YAML)

Схема строки:

```
label, translation_ru, translation_en, ai_comment, lean_status, tags
s001,  "Топологическое пространство — ...", "A topological space is ...", "Стандартное определение, см. Бурбаки §1.", verified, definition;topology
```

- Файл редактируется вручную или заполняется скриптом / агентом.
- При компиляции LaTeX/Typst читает файл и подставляет нужные поля.
- Для LaTeX — через `datatool` или Python-препроцессор; для Typst — через встроенный `csv()`.

#### 1.3 Локальный контекст

**Определение.** *Локальный контекст* в точке `P` текста — это множество меток предложений, которые:
1. идут до `P` по тексту,
2. остаются «активными» в `P` (введённый объект ещё используется, определение ещё не обобщено).

**Механизм заполнения:**

- Для каждого предложения `s_i` определяется диапазон актуальности `[s_i, s_j]` — метка первого предложения, где понятие перестаёт использоваться.
- Эти диапазоны хранятся в отдельном столбце CSV (`active_until`) или в отдельном файле `context.csv`:
  ```
  label, active_until
  s001,  s047
  s003,  s012
  ```
- При генерации подстрочника для `s_k` собираются все метки, у которых `label ≤ s_k ≤ active_until` — это и есть контекст.
- Контекст может выводиться как сноска, боковая панель (Typst `place`) или отдельный файл для передачи в LLM.

#### 1.4 Применения

| Режим | Что делает |
|---|---|
| `translation` | Под каждым предложением — строка перевода из CSV |
| `ai-comment` | Под каждым предложением — комментарий из колонки `ai_comment` |
| `lean-status` | На полях — иконка верификации (✓ / ? / ✗) |
| `context-dump` | Экспорт контекста для каждой метки в JSON, пригодный для передачи в LLM |
| `review` | Все четыре режима одновременно, на отдельных страницах |

#### 1.5 Инструменты автозаполнения CSV

- Claude skill, который получает фрагмент текста + существующий CSV и:
  - предлагает переводы непереведённых предложений,
  - вычисляет `active_until` на основе семантического анализа,
  - добавляет комментарии к нетривиальным шагам.
- Скрипт `scripts/populate_context.py` — эвристический анализ (поиск последнего вхождения ключевых слов из определения).

## 2. Stack Project как затравка для автодополнения лемм

### Идея

Использовать [The Stacks Project](https://stacks.math.columbia.edu/) как базу знаний для подсказки подходящих лемм при написании математического текста. Когда формулируется утверждение, агент ищет в Stacks Project похожие результаты и предлагает ссылки.

### Компоненты

#### 2.1 Индекс Stacks Project

- Stacks Project распространяется как набор TeX-файлов (репозиторий `stacks/stacks-project` на GitHub, ~7000 страниц).
- Из TeX-файлов извлекаются:
  - метки (`\label{lemma-foo}`),
  - формулировки лемм/теорем/определений,
  - теги (числовой идентификатор вида `04AB`).
- Строится векторный индекс формулировок (embedding) — локально через `sentence-transformers` или через Anthropic embeddings API.

#### 2.2 Claude skill `stack-lookup`

Интерфейс:

```
/stack-lookup "Морфизм конечного типа стабилен под базисной заменой"
```

Агент:
1. Эмбеддит запрос.
2. Ищет ближайшие леммы в индексе.
3. Возвращает список с тегами, формулировками и URL вида `https://stacks.math.columbia.edu/tag/XXXX`.
4. Опционально вставляет `\cite{stacks-project}[\href{...}{Tag XXXX}]` в текущий документ.

#### 2.3 Интеграция с подстрочником

- Колонка `stacks_ref` в CSV: при заполнении агент автоматически проставляет теги Stacks Project для утверждений, которые там есть.
- В режиме `ai-comment` рядом с каждой леммой показывается ссылка на аналог в Stacks Project.

#### 2.4 Расширение: другие базы

| База | Охват |
|---|---|
| Stacks Project | Алгебраическая геометрия, коммутативная алгебра |
| Kerodon | Высшие категории, ∞-категории |
| Mathlib4 | Lean-верифицированная математика (пересечение с п. 3) |
| zbMATH Open API | Широкий охват, поиск по MSC |

## 3. Lean Verification Platform как Claude skill

### Идея

Интегрировать формальную верификацию математических утверждений в рабочий процесс через MCP-инструмент [Aristotle Formal Prover](https://mcpmarket.com/tools/skills/aristotle-formal-prover-1). Каждое помеченное утверждение в подстрочнике может иметь статус верификации.

### Компоненты

#### 3.1 Claude skill `lean-verify`

```
/lean-verify s042
```

Агент:
1. Читает формулировку предложения `s042` из CSV/документа.
2. Переводит её в Lean 4 с помощью LLM (с примерами из Mathlib как few-shot).
3. Передаёт Lean-код в Aristotle Formal Prover MCP.
4. Получает результат: `verified` / `counterexample` / `timeout` / `needs_hypothesis`.
5. Записывает статус и Lean-фрагмент в CSV (колонки `lean_status`, `lean_code`).

#### 3.2 Интеграция с подстрочником

- В режиме `lean-status` на полях документа отображаются иконки:
  - ✓ `verified` — утверждение формально доказано,
  - ⚠ `needs_hypothesis` — доказано при дополнительных гипотезах,
  - ? `draft` — ещё не проверялось,
  - ✗ `counterexample` — найден контрпример (требует правки).
- Полный Lean-код хранится рядом с документом в `lean/` и компилируется независимо.

#### 3.3 Workflow

```
Написать утверждение в tex/typ
        ↓
populate_csv (перевод + Stacks ref)
        ↓
/lean-verify (Lean 4 + Aristotle MCP)
        ↓
Статус в CSV → иконка в PDF
        ↓
Экспорт контекста → передача в следующий агент
```

#### 3.4 Альтернатива: Rethlas

[Rethlas](https://github.com/frenzymath/Rethlas) — агентный фреймворк для математических рассуждений на базе LLM (без формальной верификации в Lean). Набор специализированных skills:

| Skill | Функция |
|---|---|
| `direct-proving` | Прямое доказательство через цепочку рассуждений |
| `propose-subgoal-decomposition-plans` | Разбивка доказательства на подцели |
| `recursive-proving` | Рекурсивная структура доказательств |
| `construct-counterexamples` | Поиск контрпримеров к предложенному утверждению |
| `construct-toy-examples` | Упрощённые иллюстративные примеры |
| `identify-key-failures` | Анализ того, где именно рушится попытка доказательства |
| `obtain-immediate-conclusions` | Выведение прямых следствий из посылок |
| `search-math-results` | Поиск релевантных теорем во внешних базах |
| `verify-proof` | Проверка корректности готового доказательства |
| `query-memory` | Доступ к ранее накопленным результатам |

**Сравнение подходов:**

| | Aristotle / Lean 4 | Rethlas |
|---|---|---|
| Тип верификации | Формальная (type-checked) | LLM-based (неформальная) |
| Надёжность | Абсолютная (если компилируется) | Зависит от модели |
| Охват | Формализуемые утверждения | Любые математические тексты |
| Скорость | Медленно для сложных теорем | Быстро |
| Интеграция с Mathlib | Прямая | Через `search-math-results` |

**Рекомендация для подстрочника:** использовать Rethlas на этапе черновика (быстрая проверка рассуждений, поиск контрпримеров, декомпозиция), Lean/Aristotle — для финальной формальной верификации ключевых утверждений.

#### 3.5 Прогрессивная верификация

- Начинать с верификации определений и ключевых лемм.
- Леммы со статусом `verified` автоматически добавляются как `sorry`-free в Lean-файл проекта.
- Итоговый документ может содержать аннотацию «N из M утверждений формально верифицированы».

## 4. Навык создания докладов: двухканальный Typst (доска + голос)

### Идея

Skill, который из математического текста (статьи, главы, подстрочника) собирает **доклад в Typst**, где каждый слайд хранит сразу два канала:

- **на доску** — то, что видит аудитория (формулы, тезисы, картинки);
- **вслух** — то, что докладчик произносит (speaker notes, разговорный рассказ, переходы).

Дополнительно skill **предлагает идеи визуализаций** для каждого слайда: какие диаграммы, анимации появления, геометрические картинки уместны. Принцип «доска ≠ конспект»: на доску попадает минимум символов, основная нагрузка — в голосовом канале.

### Компоненты

#### 4.1 Двухканальный шаблон слайда

Поверх Typst-движка презентаций ([Touying](https://touying-typ.github.io/) — современный аналог Beamer; `polylux` как запасной вариант):

```typ
#slide(
  board: [
    $ f: X -> Y "квазиконечный" $
    #viz-placeholder("диаграмма послойного разложения")
  ],
  speech: [
    Напомню, квазиконечность — это конечность слоёв.
    Ключевая идея: разложить морфизм через нормализацию.
  ],
  viz: "fibre diagram; подсветить особый слой красным",
)
```

- `board` рендерится на слайде.
- `speech` идёт в speaker notes (Touying `pdfpc`/`#speaker-note`) и в отдельный экспорт.
- `viz` — текстовое описание идеи визуализации (черновик для художника/агента).

#### 4.2 Режимы экспорта

| Режим | Артефакт |
|---|---|
| `slides` | Чистый PDF только с каналом `board` (для проектора) |
| `notes` | PDF/Markdown со скриптом `speech` (для докладчика, крупный шрифт) |
| `presenter` | Совмещённый вид: слайд + заметки + таймер (pdfpc) |
| `handout` | Раздаточный материал: `board` + сжатый `speech` под каждым слайдом |
| `script` | Сплошной текст `speech` без слайдов — для репетиции/перевода |

#### 4.3 Генерация из подстрочника (связь с п. 1)

- Skill принимает диапазон меток `s012–s047` и собирает черновик доклада: формулировки лемм → на доску, переводы/комментарии из CSV → в голосовой канал.
- Локальный контекст (п. 1.3) используется, чтобы напомнить слушателю ранее введённые объекты («как мы видели на слайде 3»).
- Колонка `slide_hint` в CSV: автор помечает, какие предложения обязательно выносить на слайд.

#### 4.4 Идеи визуализаций

- Skill анализирует тип утверждения и предлагает шаблон визуализации:

  | Тип содержания | Предлагаемая визуализация |
  |---|---|
  | Морфизм / отображение | Стрелочная диаграмма, коммутативный квадрат |
  | Фильтрация / башня | Вертикальная цепочка вложений с анимацией появления |
  | Индукция / рекурсия | Раскрывающиеся уровни (пошаговый `#pause`) |
  | Контрпример | Конкретная картинка-объект с подсветкой «ломающейся» части |
  | Классификация | Таблица/решётка случаев |

- Для геометрии — генерация черновика на CeTZ (Typst-аналог TikZ); для коммутативных диаграмм — `fletcher`.
- Идеи выдаются как комментарии `viz:`; их можно дорабатывать вручную или передавать отдельному агенту-иллюстратору.

#### 4.5 Контроль длительности

- Эвристика: ~110 слов `speech` ≈ 1 минута. Skill суммирует голосовой канал и предупреждает о перерасходе на докладе фиксированной длины (20/45/60 мин).
- Режим `script` даёт точную оценку и помечает слайды-кандидаты на сокращение.

## 5. Доказательство «на примере»: расширение разметки tags

### Идея

Расширение системы меток и тегов из п. 1: для абстрактного доказательства параллельно ведётся **прогон того же рассуждения на конкретном примере**. Каждый шаг общего доказательства сопровождается его реализацией на выбранном объекте — читатель видит абстрактную логику и её конкретную тень одновременно.

Цель — «work proofs through some example»: понизить порог входа, ловить ошибки (если шаг не проходит на примере — он подозрителен) и автоматически порождать иллюстрации для доклада (п. 4) и комментарии подстрочника (п. 1).

### Компоненты

#### 5.1 Новый тег и парные метки

- В колонку `tags` (п. 1.2) добавляется значение `example-track`.
- Помимо метки предложения `s042` вводится **зеркальная метка** `s042@ex` — тот же шаг, развёрнутый на конкретном примере.
- В CSV появляются колонки:

  ```
  label, example_subject, example_step
  s042,  "X = Spec k[x,y]/(xy)",  "Здесь слой над 0 — две точки, морфизм квазиконечен."
  ```

- `example_subject` фиксируется один раз на блок доказательства (например, на лемму); `example_step` заполняется построчно.

#### 5.2 Режимы рендеринга

| Режим | Что делает |
|---|---|
| `parallel` | Две колонки: слева общее доказательство, справа прогон на примере |
| `inline-example` | Под каждым шагом — серая строка «на примере: …» |
| `example-only` | Только конкретный прогон (учебная версия без абстракции) |
| `gap-check` | Подсвечивает шаги без заполненного `example_step` — кандидаты на скрытую ошибку или непроверенный переход |

#### 5.3 Автозаполнение примера (skill)

- Skill `work-through-example` получает доказательство + выбранный (или предложенный им) пример и:
  1. подбирает «минимальный нетривиальный» объект для `example_subject`;
  2. прогоняет каждый шаг на этом объекте, заполняя `example_step`;
  3. помечает шаги, где пример **не проходит** (потенциальный пробел в доказательстве) — пересекается с `construct-counterexamples` из Rethlas (п. 3.4);
  4. опционально порождает CeTZ-картинку примера для доклада (п. 4.4).

#### 5.4 Связь с верификацией

- Шаг, прошедший и на примере (п. 5), и формально в Lean (п. 3), получает повышенный уровень доверия.
- Несовпадение «общий шаг verified, но на примере ломается» сигнализирует об ошибке формализации — полезный кросс-чек.

## 6. Воркфлоу «из научного вопроса в статью»

### Идея

Сквозной оркестратор, проводящий исследование от **постановки вопроса** до **готовой статьи и доклада**, связывая воедино существующие скиллы проекта (`deep-research`, `academic-paper`, `academic-paper-reviewer`, `academic-pipeline`) и инфраструктуру из пп. 1–5. Каждая стадия оставляет артефакт, на который опирается следующая; подстрочник (п. 1) служит общей шиной данных между стадиями.

### Компоненты

#### 6.1 Стадии

```
[0] Вопрос          — формулировка: что хотим понять/доказать
        ↓ deep-research (Socratic), brainstorming
[1] Разведка        — литература (Stacks/zbMATH, п. 2), известные результаты
        ↓ stack-lookup, search-math-results
[2] Гипотеза        — точное утверждение + ожидаемая трудность
        ↓ Rethlas: subgoal-decomposition, toy-examples (п. 3.4)
[3] Исследование    — попытки доказательства, контрпримеры, прогон на примере (п. 5)
        ↓ work-through-example, lean-verify (п. 3)
[4] Костяк          — верифицированные леммы + подстрочник с метками (п. 1)
        ↓ academic-paper (outline → draft)
[5] Текст           — статья в Typst/LaTeX, переводы из CSV
        ↓ academic-paper-reviewer (две стадии, integrity check)
[6] Рецензия        — правки по замечаниям рецензентов
        ↓ revision
[7] Доклад          — презентация из подстрочника (п. 4)
        ↓ доклад-skill
[8] Публикация      — финальный PDF + слайды + Lean-приложение
```

#### 6.2 Skill-оркестратор `question-to-paper`

- Тонкая обёртка над `academic-pipeline`, добавляющая математические стадии (Lean/Rethlas/пример) и фиксирующая состояние проекта в одном месте.
- Хранит **журнал стадии** (`project/state.yaml`): на какой стадии находится проект, какие леммы доказаны/верифицированы, какие вопросы открыты.
- На каждой стадии вызывает соответствующий существующий skill и кладёт результат в подстрочник/CSV.

#### 6.3 Карта вопросов (research log)

- Открытые подвопросы хранятся как метки со статусом: `open` / `conjectured` / `proved` / `verified` / `dropped`.
- Связь «вопрос → леммы, которые его закрывают» — через те же метки подстрочника.
- В любой момент можно собрать сводку: «из 7 подвопросов 4 доказаны, 2 верифицированы в Lean, 1 открыт».

#### 6.4 Точки ветвления

| Исход стадии | Переход |
|---|---|
| Контрпример к гипотезе (п. 3/5) | Назад к [2]: переформулировать утверждение |
| Литература: результат уже известен | К [5] напрямую (обзор/экспозиция) или смена вопроса |
| Рецензент нашёл пробел | К [3] для конкретной леммы, не всей статьи |
| Доказательство не формализуется | Оставить `needs_hypothesis`, пометить в статье честно |

## Зависимости

Порядок и группировку работ см. в разделе [«Дорожная карта по этапам»](#дорожная-карта-по-этапам) выше. Граф зависимостей между подсистемами:

```
[1. Подстрочник] ←──────────── базовая инфраструктура (шина данных) для всего
   ↑        ↑        ↑
[2. Stack] [4. Доклад] [5. Пример] ← все читают/пишут метки и CSV из п. 1
   ↑                      ↑
[3. Lean verify] ←────────┘  ← п. 5 даёт кросс-чек, п. 2 даёт Mathlib

[6. Вопрос → статья] ← оркестрирует 1–5 + существующие academic-* скиллы
```

Соответствие подсистем фазам:

| Раздел (подсистема) | Реализуется в фазах |
|---|---|
| 1. Подстрочник | 0 (MVP), 1 (контекст), 5 (`review`) |
| 2. Stacks lookup | 2 |
| 3. Lean verify | 4 |
| 4. Доклад | 5 |
| 5. Прогон «на примере» | 3 |
| 6. Вопрос → статья | 6 |

Одна подсистема может достраиваться в нескольких фазах (например, подстрочник: каркас в Ф0, контекст в Ф1, сводный `review` в Ф5) — это и есть принцип вертикальных срезов.
